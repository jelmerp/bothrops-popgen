That confirms it. Your VCF is an **all-sites (monomorphic-included) freebayes VCF** — it has a record at nearly every base position of the locus (684 records for an 800bp locus), not just at variant sites. Look at the example above: `ALT=.` with `GT=0/0` — these are invariant reference positions, one per base, not actual variant calls.

So the "hom-ref per-locus count" isn't counting distinct hom-ref *variants* — it's essentially counting **how many bases in the locus have a confident, non-missing homozygous-reference call**. A mean of ~600 for an ~800bp locus just means most of the locus is covered and called reference in that sample (with ~135 positions missing/no-call and a handful of real variants).

This changes the interpretation of all three metrics:
- **hom-ref count** ≈ number of reference bases covered/called (site-count, not variant-count)
- **het / hom-alt counts** ≈ number of positions with an actual variant genotype (these should be small, since only real SNPs/indels get 0/1 or 1/1)
- Comparing het+hom-alt to hom-ref effectively gives you **callable breadth of the locus**, while het/hom-alt counts alone tell you about actual variation found.

So the large hom-ref numbers aren't a bug — they reflect freebayes emitting monomorphic sites — but if your intent was "average number of heterozygous/homozygous-alt **variants** per locus," that's still valid from the het/hom-alt files; the hom-ref number is really a proxy for "how much of the locus had reference-confidence coverage," which is a different, and probably more useful, QC signal (locus callability) than you may have assumed.

### Assistant — 2026-09-10 17:36:57

No — it's not allele-based, and there's no doubling. Each VCF record contributes exactly 1 to the count if its genotype matches the category, regardless of ploidy. `GT="RR"` is bcftools syntax for "this sample's genotype is homozygous reference" (i.e. `0/0`) — it's a per-site classification, not a per-allele one.

The actual mechanism: `bedtools intersect -c` counts the number of **VCF records (rows)** from the filtered stream that fall inside each locus interval. Since this is an all-sites freebayes VCF (a record at nearly every base position, as I showed earlier — e.g. `POS=125612965, ALT=., GT=0/0`), there's roughly one row per base pair in the locus, not one row per variant.

I verified this concretely earlier for the Binsu_ma-1 / L1000 locus (800bp): `bcftools query` showed exactly **544 records with GT=0/0** in that region, and the hom-ref-per-locus file reports **544** for that same locus. One-to-one match — 544 rows in, 544 in the count, no multiplication by 2.

So the large number is because **1 row ≈ 1 base position**, and most base positions in a locus are confidently called homozygous-reference — not because each hom-ref genotype is being counted as 2 alleles.
